# SurfaceLab

A deliberately vulnerable Android training app covering six modern mobile attack surfaces. All accounts, invoices, tokens, AES data keys, and flags are synthetic and generated by this project.

The repository builds three independently installable APKs:

| APK | Package | Purpose |
| --- | --- | --- |
| `surfacelab-vulnerable.apk` | `com.example.vulnerable` | Six intentionally vulnerable labs |
| `surfacelab-hardened.apk` | `com.example.hardened` | A comparison implementation with narrower trust boundaries |
| `surfacelab-probe.apk` | `com.example.labprobe` | Ordinary companion app demonstrating cross-UID interactions |

## Build and install

Use Android Studio or JDK 17/21, Android SDK platform 35, and build tools 35.0.0. The Gradle wrapper pins Gradle 8.9 and AGP 8.7.3; AndroidX Core 1.15.0 supplies the actual FileProvider. Minimum Android version is 9 / API 28, and the apps target API 35. These versions are deliberately pinned for a reproducible lab, rather than following latest releases.

Open this folder in Android Studio and let SDK discovery create `local.properties`, or set `ANDROID_HOME` to your SDK location. On Windows:

```powershell
.\gradlew.bat :app:assembleVulnerableDebug :app:assembleHardenedDebug :probe:assembleDebug
adb devices -l
adb -s emulator-5554 install -r app/build/outputs/apk/vulnerable/debug/app-vulnerable-debug.apk
adb -s emulator-5554 install -r app/build/outputs/apk/hardened/debug/app-hardened-debug.apk
adb -s emulator-5554 install -r probe/build/outputs/apk/debug/probe-debug.apk
```

On macOS/Linux run `chmod +x gradlew` if needed, then use `./gradlew`. Packaged APKs, when built in this workspace, are also copied to `artifacts/`. Select an emulator or a dedicated training device. Start **SurfaceLab** once, then open **SurfaceLab Probe**. The probe has a **Switch target** button to compare both builds. It requires no storage, accessibility, or root permission.

## Labs

| Lab | Vulnerable behavior | Hardened comparison |
| --- | --- | --- |
| 01 · Deep links & WebView | `myapp://transfer` performs a synthetic transfer without authentication; arbitrary loaded pages can read a synthetic session through `LabSession` | External transfer routes are rejected; URL input is restricted to an exact local page, JavaScript is disabled, and the bridge is absent |
| 02 · FileProvider grants | `<root-path>` plus an exported broker grants a caller read access to the victim's private files | The provider exposes only `cache/published/`; the broker shares only the public handout |
| 03 · Biometric vault | UI-only biometric callback; a non-authenticated Keystore wrapping key; cached plaintext AES data key | Per-use biometric private-key operation via `CryptoObject`; no static plaintext key cache; `FLAG_SECURE` |
| 04 · Mutable PendingIntent | An exported ticket broker returns a mutable empty-intent ticket with `FILL_IN_COMPONENT` permission; the probe supplies the private admin destination | Explicit, immutable ticket always opens the harmless receipt screen |
| 05 · Forensics | Inclusive backup rules, external invoice PDF, live SQLite/WAL, unprotected recent-app screen | Sensitive fixtures in `noBackupFilesDir`, restrictive backup rules, protected vault and evidence screens |
| 06 · Anti-Frida & runtime hooks | A centralized detector scans real process mappings and terminates the app when Frida is found; bypass it, intercept the protected report, and submit its per-challenge flag | The same guard remains hookable, but the separate hardened payload supplies only a public receipt and contains no Lab 6 secret generator |

The probes exercise real Android APIs. There is no simulated "exploit succeeded" switch. Lab observations on the dashboard are an aid to demonstrations, rather than a grading or authentication mechanism. The forensics observation is marked manually; use the collection script to acquire the actual evidence.

For Lab 6, tap **Open runtime challenge** on the dashboard. Use `scripts/frida-runtime-bypass.js` for the first stage and `scripts/frida-runtime.js` for both stages. The report remains hidden on the normal screen; only submitting the correct flag completes the vulnerable challenge. Frida requires an instrumentable training device or emulator and a matching server or Gadget setup. See [the Lab 6 walkthrough](docs/DEMO_GUIDE.md#6-anti-frida-detection-and-runtime-secret-recovery). The hardened comparison demonstrates avoiding a local secret; it does not claim that instrumentation can be made impossible.

Start with [the cracking walkthrough](CRACKING_README.md) for exact commands, expected flags, hardened comparisons, and reset steps. Read [the presenter demo guide](docs/DEMO_GUIDE.md) for additional context and acquisition limits. Read [the technical notes](docs/TECHNICAL_NOTES.md) for source locations and corrections to the supplied concepts. See [validation results](docs/VALIDATION.md) for what was actually tested.

## Verification and collection

Build the two small on-device test packages, install them, then run the smoke script:

```powershell
.\gradlew.bat :app:assembleVulnerableDebugAndroidTest :app:assembleHardenedDebugAndroidTest
adb -s emulator-5554 install -r app/build/outputs/apk/androidTest/vulnerable/debug/app-vulnerable-debug-androidTest.apk
adb -s emulator-5554 install -r app/build/outputs/apk/androidTest/hardened/debug/app-hardened-debug-androidTest.apk
python scripts/smoke.py --serial emulator-5554
python scripts/check_webview.py --serial emulator-5554
python scripts/collect.py --serial emulator-5554
```

With `frida` and `frida-tools` installed in the selected Python environment and a matching Frida server listening on the training emulator, run the real Lab 6 checks:

```powershell
python scripts/check_runtime.py --serial emulator-5554
```

This verifies actual agent detection and process termination, the detector-only bypass, report interception, flag submission, and the hardened public-only payload. It selects the device explicitly and removes its temporary ADB forwarding when finished. Evidence is saved to `artifacts/evidence/runtime.json`.

Pass `--adb C:/path/to/adb.exe` if it is not on `PATH`. Both scripts require an explicit serial so they cannot silently choose a device. The smoke run creates synthetic transactions and exports a synthetic audit. Collection force-stops only the selected lab package before copying its debug sandbox. This uses authorized `run-as` debugging access, not a sandbox bypass or `adb backup`.

Clear app storage to regenerate fixtures and remove the wrapping key. Dashboard reset clears only observations. Uninstall all three packages to remove internal files; remove any manually exported audit in Downloads separately.

## Layout

```text
app/          Target app, vulnerable/hardened flavors, on-device checks
probe/        Separate-UID companion application
shared/       Small native Android UI toolkit
scripts/      Frida demonstration, loopback web collector, smoke and collection tools
docs/         Demo guide, implementation notes, validation record
artifacts/    Ready-to-install APKs and source archive
```

Both comparison APKs are debuggable lab builds. The hardened flavor illustrates specific mitigations; its debug extraction surface and intentionally public training screens make it unsuitable as a production security template.
